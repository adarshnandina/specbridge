# Experiments

All tables on this page are generated by a script from the run files in `eval_results/`
(`python -m specbridge.eval.experiments --split dev|test --render`; the page itself by
`scripts/dev/render_docs.py`); each row carries its run id. Prose that quotes a number was written
against these runs.

## Setup and decision rules

- **Corpus:** 51 synthetic datasheets + 9 real datasheets in the same index (the real ones act as
  distractors; no retrieval question targets them): 60 documents, 264 layout chunks. Embeddings:
  `BAAI/bge-small-en-v1.5`.
- **Retrieval questions:** QA items that have expected sources (unanswerable items excluded):
  **dev n=56, test n=37**. A *hit* is a retrieved chunk from an expected `doc_key` **and** an expected page.
- **Cost:** retrieval experiments make no LLM calls (`provider=fake`, cost $0).
- **Protocol (set before looking at test):** configurations are chosen on **dev**. A difference is only
  called an improvement if the two 95% Wilson intervals of recall@5 are disjoint (`significant`);
  `weak` = partial overlap, `within noise` = at least half of the narrower interval overlaps. When a
  difference is within noise the default is left unchanged, or the simpler/cheaper option is preferred.
  **Test** is then run once for confirmation; it is not used to tune.
- MRR is a mean of reciprocal ranks and has no Wilson interval; its delta is shown without a noise flag.
- **Small samples:** with n=56 / 37 the intervals are wide. Treat anything but large effects as unresolved.

## A reproducibility bug found by a clean checkout (read this first)

My first pass of these experiments (run ids `20261118-1346...` to `20261118-1351...`, kept in
`eval_results/` and indexed in `eval_results/_superseded/experiments_*_pre-determinism.json`)
reported hybrid recall@5 = 0.911 on dev. A fresh checkout (new database, same corpus, same code)
measured **0.839**, and 17 of 56 questions ranked differently. Cause: ties in the keyword and vector
rankings were broken by `chunks.id`, a random UUID that differs per database, so results depended on
ingest order. Fixes: ties are now broken by `(doc_key, chunk_index)`, and keyword ties share a rank
inside the fusion (`competition_ranks`/`rrf_scored`). Verified: two independent indexes of the same
corpus now give identical ranks for all 56 questions. **All numbers below were re-measured after the
fix; the first-pass numbers are not used for any decision.** The same hybrid configuration
measured 0.91, 0.84 and (deterministic) 0.77 recall@5 on dev depending on tie order: a spread more
than four times the gate threshold (0.03).

## Experiment 1 - chunking (`fixed` vs `layout`, and a control)

**Hypothesis:** layout-aware chunks (headings, tables as their own chunk, context header) retrieve
better than fixed 300-token windows. **Control added:** layout chunks carry a context header and fixed
chunks do not, so a third index (`fixed` + header) separates the two effects.

{d0}

Test (confirmation):

{t0}

**Interpretation.** Layout chunks beat plain fixed chunks by a margin that is only *within noise* on
dev (recall@5 0.768 vs 0.679) and *weak* on test (0.865 vs 0.703). Fixed chunks **with the context
header** are numerically at least as good as layout chunks on both splits (dev 0.893 vs 0.768, flagged
`weak`; test 0.865 vs 0.865). So on this corpus there is **no evidence that layout-aware chunk
boundaries improve retrieval**; the header (experiment 4) is what matters. **Decision:** keep
`CHUNK_STRATEGY=layout` (changing it needs a re-ingest and layout chunks give a table its own
bounding box for precise citation highlights, a benefit this retrieval benchmark does not measure),
but do not claim it helps retrieval. If only retrieval quality mattered, fixed + header would be the
simpler choice.

## Experiment 2 - retrieval mode (`vector` vs `keyword` vs `hybrid`)

**Hypothesis:** hybrid (RRF over vector + keyword) beats either alone.

Dev:

{d1}

Test (confirmation):

{t1}

**Interpretation.** Keyword-only search is significantly worse than both alternatives. **Hybrid did
not beat vector-only; it was worse on every metric on both splits** (dev recall@5 0.768 vs 0.875,
recall@1 0.518 vs 0.607; test 0.865 vs 0.892, recall@1 0.622 vs 0.757), although with these sample
sizes the recall@5 intervals overlap (`within noise`). Fusing a weak keyword ranking dilutes the top
ranks, and it is the component whose ordering was unstable (see the bug above). **Decision (changed
from my first pass):** by the protocol, within noise means prefer the simpler/cheaper option, and
vector-only is simpler, faster, deterministic and never behind. **`RETRIEVAL_MODE=vector` is now the
default**; `hybrid` and `keyword` remain selectable per call. Revisit with real datasheets whose
part numbers may stress embeddings differently.

## Experiment 3 - cross-encoder reranker

**Hypothesis:** reranking the top 20 candidates with `BAAI/bge-reranker-base` improves precision at the
cost of latency. (Measured on the hybrid candidate pool; the vector row is shown for context.)

Dev:

{d2}

Test (confirmation):

{t2}

**Interpretation.** The first implementation made retrieval **much worse** (recall@5 0.589,
`20261118-134620_ba6fde4_exp3-hybrid-rerank`, a pre-fix run kept for the record): the reranker scored the bare
chunk content, and a table chunk alone does not say which part it describes (that lives in the context
header). After changing the reranker input to *context header + content* (the text the embedder sees;
regression test `test_reranker_sees_context_header_and_content`) it improves the top ranks strongly: dev
recall@1 0.893 vs 0.518 (hybrid) and 0.607 (vector), recall@5 0.964 vs 0.768 (`significant` against
hybrid) and 0.875 (vector, within noise). It costs about 800 ms per query on CPU versus about 20 ms.
**Decision:** `RERANK_ENABLED=false` by default: against the new default (vector) the recall@5 gain is
within noise and the latency is ~40x; turn it on when the single best chunk matters more than latency.

## Experiment 7 - `ABSTAIN_MIN_SCORE` calibration

**Question:** can the best vector similarity of the retrieved chunks be used to abstain *before* calling
the LLM? The sweep treats "abstain iff best similarity < t".

Dev (where the threshold would be chosen):

{d4}

Test (confirmation):

{t4}

**Interpretation.** The retrieval score barely separates answerable from unanswerable questions (mean
best similarity 0.705 vs 0.672 on dev, 0.713 vs 0.675 on test). Missing-attribute questions about a real
part and non-existent part numbers still retrieve plausible chunks. On dev a threshold of 0.60 blocks 2
of 9 unanswerable questions and no answerable one, but on test the same threshold blocks 1 of 37
answerable questions and 0 of 6 unanswerable ones; higher thresholds trade away answerable questions
faster than they catch unanswerable ones. **Decision:** `ABSTAIN_MIN_SCORE=0.0` (retrieval-score
abstention disabled). Abstention relies on the model's `answerable` flag and citation verification,
which depend on the LLM and are **not yet measured against a real model** (blocked: needs API key).

## Summary of decisions

| setting | value | evidence |
|---|---|---|
| `CHUNK_STRATEGY` | `layout` | no retrieval evidence either way (fixed + header numerically >= layout); kept for citation highlights (exp 1) |
| context header | on | large effect, dev significant, confirmed on test (exp 4) |
| `RETRIEVAL_MODE` | **`vector`** (was `hybrid`) | hybrid not better on any metric and was the unstable component (exp 2) |
| `RERANK_ENABLED` | `false` | strong top-rank gain but ~800 ms; recall@5 within noise vs vector (exp 3) |
| `ABSTAIN_MIN_SCORE` | `0.0` | no threshold generalises from dev to test (exp 7) |
| extraction model / retry | unchanged defaults | blocked: needs API key (exp 5, 6) |

The final baseline and test-split report are listed in [EVALUATION.md](EVALUATION.md).
