# Limitations

This list is meant to be read before trusting any number in this repository.

## What has and has not been measured

- **No real-LLM result exists yet.** `ANTHROPIC_API_KEY` was not set during the build, so every QA,
  extraction and agent number in `eval_results/` comes from the **fake provider** (an extractive
  answer heuristic, a regex extractor, a constant judge, scripted agent behaviours). Those runs are
  *pipeline checks*; each result file says so. Specifically unmeasured: answer accuracy of a real
  model, real abstention behaviour, real citation precision/coverage, real extraction F1 and the
  precision of validated records, experiments 5 and 6 (model choice, retry loop), and any live agent
  run. Commands to produce them are in `docs/EVALUATION.md` and `docs/EXPERIMENTS.md`; one dev QA run
  is estimated at about $0.035 by the runner.
- **Retrieval numbers are real but come from a small, synthetic benchmark:** dev n=56, test n=37.
  A recall@5 of 0.88 has a 95% interval of roughly 0.76-0.94 (dev, `20261118-142407_f14eb9c_baseline-dev-all`) and about 0.75-0.96 (test, `20261118-142424_f14eb9c_final-test-all`). Only large
  effects are resolved (header on/off, fixed vs layout without header, keyword-only). Differences such
  as hybrid vs vector-only or layout vs fixed-with-header are **within noise** and are reported that way.
- **The judge is uncalibrated.** `eval/datasets/judge_calibration.jsonl` has empty `human_score`
  fields; until a human fills them in, judge scores must be read as uncalibrated (and with the fake
  provider the judge is a constant).

## Data and labels

- **Synthetic data bias.** The 51 synthetic datasheets are generated by templates written by the same
  author as the extractor and the questions. They contain deliberate format variety but are cleaner
  than real documents (one product per sheet, regular tables, no scans, no marketing prose, no
  multi-product catalogues). Results on them are an optimistic bound. The QA questions are
  template-generated, so phrasing diversity is low.
- **Real-datasheet labels are provisional.** `eval/datasets/extraction_real.jsonl` (9 documents) was
  drafted by Claude from the PDF text and is `verified_by_human: false` everywhere; ambiguous values
  (e.g. "IP67/IP69K", "88-132 / 176-264 V AC") were resolved by a documented rule, not by an expert.
  Fewer real datasheets than the 10-20 target were obtained: several vendor sites block automated
  downloads. A person must verify these labels before the numbers mean anything.
- **Real datasheets are not redistributed.** `corpus/real/manifest.yaml` lists URLs and checksums; one
  document (Wachendorff DRA10-24) embeds the download date in its text, so its checksum changes daily
  and `fetch.py` will warn.
- **Ground-truth scope.** Agent scenarios seed approved extractions from the synthetic ground truth
  rather than from extraction output, so they test the agent, not the extractor.

## Parsing and retrieval

- **PDF parsing:** PyMuPDF text and `find_tables()`. Scanned PDFs (no text layer), rotated text,
  merged/nested table cells, multi-column prose with irregular reading order and vector-drawn tables
  without ruling lines are not handled (no OCR). Wrapped table cells can split a value across lines
  (the rule-based fake extractor loses `UKCA` that wraps in layout (b) for this reason).
- **Citation highlight boxes** for tables come from `find_tables()` and cover the text extent, not
  always the full drawn grid. Fixed-size chunks highlight one union box over several blocks.
- **Keyword search is Postgres full-text search** (`websearch_to_tsquery('simple', ...)`,
  `ts_rank_cd`), **not BM25**; the OR-combined content-word query is a weak ranker (keyword-only recall@5 0.464
  on dev, `20261118-142214_f14eb9c_exp2-mode-keyword`). Part numbers are matched as tokens, not by edit distance.
- **Hybrid vs vector:** vector-only is the default because hybrid was worse on this corpus (EXPERIMENTS.md, experiment 2); real part numbers may favour keyword matching, which is untested.
- **Abstention.** The retrieval-score threshold does not generalise from dev to test, so it is disabled
  (`ABSTAIN_MIN_SCORE=0.0`). Abstention depends on the LLM's `answerable` flag and on citation
  verification, which are unmeasured with a real model.
- **Citation verification** is fuzzy string matching (`partial_ratio >= 90` after dash/ellipsis/pipe
  normalisation). It proves the quote exists in the source, not that it supports the claim.
- **English only.** Prompts, alias maps, unit words and question templates are English; German decimal
  commas and dashes are handled, German prose is not.
- **Reranker:** `bge-reranker-base` on CPU adds ~800 ms per query (p50 about 800 ms vs about 20 ms without it, runs `20261118-142216_f14eb9c_exp3-hybrid-rerank` and `20261118-142212_f14eb9c_exp2-mode-vector`); it is off by default.

## Extraction

- Validation is deterministic but cannot detect a *plausible, quoted, wrong* value (the fake extractor
  reading the "301" in "AL-PSU-301" as a power value passes every check). The suite reports the
  precision of validated records for exactly this reason; with a real model it is unmeasured.
- A field is a single value: variants/option tables (several ratings on one sheet) are reduced to one
  value by a documented rule ("the one that applies to the title, else the highest").
- Pint covers common units; tilde/other range notations and non-SI units beyond those tested are not guaranteed.

## Agent

- Safety is enforced in code (allowlists, approval row, four-eyes, idempotency) and tested with
  scripted adversarial model behaviour. It was **not** tested with a real model, which may fail in
  ways the scripts do not cover. The injected text can still *influence the ranking* (S10 shows the
  model's claim citing the attack text verifies against the source); the defence is that a human
  approves and the write tool is gated, not that the content is filtered.
- Candidate search uses extracted specs only; if the extractions are wrong, the candidates are wrong.
- The 120 s step limit is checked after a step completes; a blocked LLM call is bounded by `LLM_TIMEOUT_S`, not pre-empted.
- Runs execute synchronously inside the HTTP request that starts or approves them.

## Architecture and operations

- **Single node.** One API process, one Postgres, in-memory rate limiter state (per process), a local
  data directory for PDFs and page-image cache. No horizontal scaling, no HA, no queue.
- **Synchronous architecture** (ADR-0008): a worker is blocked for the duration of each LLM call.
- **Mock ERP.** The ERP is a SQLite-backed stand-in with injected faults; a real ERP will have
  different idempotency, auth and error semantics.
- **Auth** is static API keys from the environment with four roles; there is no user management, key
  rotation, SSO or per-resource ownership. The UI session cookie is `HttpOnly; SameSite=Strict`, with
  no CSRF token beyond that.
- **Rate limiting** is per API key per process (moving window); behind several workers the effective
  limit multiplies.
- **Budget guard** sums today's cost from `llm_calls`; concurrent requests can overshoot by the cost of the in-flight calls.
- **Image size** is 2.67 GB (CPU PyTorch + model); see ADR-0009.
- **Not deployed.** Deployment files and docs exist; nothing was run on a VM or cloud. `docker-compose.prod.yml`
  and the Caddyfile were never executed, and the GitHub Actions workflow was never run (no remote exists).

## What would change for production at a client

1. Run the real-model evaluations, verify the real labels, score the judge calibration set, and re-baseline.
2. Replace the mock ERP; agree idempotency and error contracts; add an outbox for change requests.
3. Move LLM-heavy work (extraction, agent runs) to a queue with workers; make approvals resume asynchronously.
4. Real identity (OIDC), key rotation, per-tenant data separation, CSRF protection, shared rate-limit store.
5. OCR for scans; table-structure recognition for complex tables; a larger, human-written question set
   with real engineers' phrasing; an evaluation set drawn from the client's own datasheets.
6. Observability to a real backend (the structured logs and Prometheus metrics are ready), alerting on
   budget, ERP failure rate and stuck approvals; backup/restore drills.
7. A smaller embedding runtime (ONNX/quantised) or an embedding service; a vector store review at scale.
